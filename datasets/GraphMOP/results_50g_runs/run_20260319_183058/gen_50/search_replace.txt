<DESCRIPTION>
Replace the one-shot static regret ordering with a tiny dynamic-regret active-pool scheduler.
Instead of computing regret only once at zero load, this recomputes best/second-best choices for a small pool of currently unassigned tasks under current server loads, then assigns the highest-regret task next.

Why this should help:
- Static regret gets stale quickly as server queues fill.
- Dynamic regret better protects “fragile” tasks (few feasible low-cost options), reducing late overload and queue spikes.
- Active-pool limits runtime overhead versus full global recomputation.
- A mild scarcity term improves feasibility and stabilizes both latency and energy.

This is a targeted edit in the assignment layer only; path validity and fallback behavior remain robust.
</DESCRIPTION>
