<DESCRIPTION>
Introduce a dynamic regret active-pool constructor for assignment order.  
Instead of committing directly to the single highest-priority source each step, we now:

1. Recompute regret with current server loads (still fully dynamic).
2. Build a small active pool of highest-regret sources.
3. Choose the source within that pool whose best feasible assignment has the lowest immediate marginal delta.
4. Keep a regret-aware fallback if feasibility is tight.

This keeps the beneficial regret signal (protecting constrained tasks) while reducing greedy over-commitment that can hurt latency/energy later due to queue buildup. I also slightly adjust the priority formula to avoid favoring high primary cost too aggressively.
</DESCRIPTION>
