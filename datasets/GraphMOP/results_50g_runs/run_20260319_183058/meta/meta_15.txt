# GLOBAL INSIGHTS SCRATCHPAD

The following are global insights about optimization approaches and their effectiveness:

## Successful Algorithmic Patterns
- **The current best result strengthens the case for server-rooted multi-tree preprocessing plus load-aware greedy assignment.** The current best program scores **5.215922** with **latency 2.304111** and **energy 1.959833**, slightly improving on **Generation 17 / Multi-Tree Load-Aware Task Routing** at **5.22, 2.30, 1.96** and on **Generation 12 / Lambda-Dijkstra Local Search Routing** at **5.24, 2.30, 1.97**. Its key change is combining **four server-rooted Dijkstra trees per server** with a stronger assignment score using **route latency, route energy, queue delay, dynamic compute energy, idle-power activation, and utilization**.
- **Marginal server-cost modeling continues to matter more than expensive post-processing.** As already suggested by prior insights, strong assignment scoring can compensate for limited route diversity. The current best preserves the efficient precompute-once-per-server structure, but improves decisions with explicit projected-load evaluation (`pred`, `util`, `qd`, compute energy, activation energy), which appears to explain the small but consistent gain over earlier valid multi-tree and lambda-search variants clustered around **5.22–5.24**.
- **Moderate candidate diversity is useful when kept within a bounded implementation.** The current best uses **four blended shortest-path trees per server** and caps each source at **12 candidates** after deduplication and sorting. This is a successful middle ground between the weaker single-scalar/fixed-path methods from prior insights and the much heavier all-profile/all-pair candidate generation in **Generation 6** and **Generation 7**, which timed out.
- **A lightweight improvement pass can help when the main assignment state is already incremental and compact.** The current best performs only a **one-pass reassignment over heavy tasks**, unlike the timeout-prone repeated local search in **Multi-Profile Dijkstra Local Search** and simulated annealing in **Multi-Profile SA Task Routing**. This preserves correctness and runtime while still refining server placement.

## Ineffective Approaches
- **Per-server, per-profile shortest-path expansion combined with heavy local search remained too expensive.** **Generation 6 / Multi-Profile Dijkstra Local Search** and **Generation 7 / Multi-Profile SA Task Routing** both ended at **-999999999.00** due to **Compilation/Runtime Timeout**. In both cases, repeated shortest-path runs plus many reconstructed source/server/profile paths and a long iterative improvement loop overwhelmed the 12-second limit.
- **Sophisticated heuristics without a complete, efficient routing pipeline produced no usable result.** **Generation 16 / Queue-Energy Heuristic Cost Function** had a detailed queue/energy scoring model, but still failed with **-999999999.00** and timeout. The summary explicitly indicates that the surrounding routing procedure or integration was missing, too slow, or fragile, so the cost model alone did not translate into a valid solution.
- **Fragile fallback/reachability assumptions were repeatedly associated with invalid runs.** The feedback for **Generation 7** notes that its fallback path construction assumed reachability, contributing to correctness/validation failures in addition to timeout. This contrasts with the current best, which defensively reconstructs paths from stored parents and includes explicit fallback logic.
- **Expensive exactness without bounded candidate control was counterproductive.** The timeout failures all share the pattern of trying to materialize many source-server-profile path combinations or repeatedly rescore assignments globally. The valid top performers instead bound candidate count and avoid full recomputation in refinement.

## Implementation Insights
- **What makes the current best effective is the exact structure of its bounded preprocessing.** For each server it runs only **four Dijkstra trees**, each with a different `(latency, energy, capacity)` blend and representative payload. It then reconstructs source-to-server paths from those trees and recomputes **true path latency and energy for each task’s actual payload**. This keeps preprocessing compact while still giving the assignment phase multiple route tradeoffs.
- **The current best’s assignment objective is its clearest implementation advantage.** For each candidate it computes a score of the form  
  `rlat + queue_delay(pred, mu) + weight * (route_energy + compute_energy) + utilization_penalty`,  
  with explicit **server activation cost** when a server goes from zero users to one. This is closely aligned with earlier global insight that the strongest family is driven by a good marginal placement model, and it likely explains the edge over **Generation 17**, whose summary describes a similar but slightly less calibrated weighted load-aware scoring.
- **The queue-delay implementation is deliberately strong near saturation and likely stabilizes correctness/performance.** The current best uses a hard penalty past about **98.5% of service rate** and rejects assignments near **99.2% / 99.4%** utilization during greedy and local-improvement phases. This matches prior global observations that strong near-saturation penalties correlate with robust valid solutions.
- **Defensive path handling is a recurring success factor in valid programs.** The current best uses `reconstruct_to_server` from stored parents, verifies path metrics via `edge_attr`, and falls back to a single-source mixed-weight Dijkstra when needed. This conservative coding style mirrors previous insight that reliable fallback behavior separates passing solutions from richer but fragile implementations such as **Generation 7**.

## Performance Analysis
- **The current best is now the strongest explicitly reported valid program, but only by a very small margin.** It achieves **score 5.215922**, beating **Generation 17** at **5.22** and **Generation 12** at **5.24**. The improvement is narrow, reinforcing the previous conclusion that the search is operating on a tight frontier where implementation details in the assignment model matter more than large structural changes.
- **The best-performing valid programs remain tightly clustered in both objectives.** The current best has **latency 2.304111** and **energy 1.959833**, compared with **Generation 17** at about **2.30 / 1.96** and **Generation 12** at **2.30 / 1.97**. This supports the repeated evaluator feedback that the remaining gap is not a simple latency-vs-energy tradeoff; the strongest methods improve both together only incrementally.
- **Runtime-feasible precomputation clearly dominates heavy search-based approaches in observed results.** All valid top methods use some form of **precomputed server-rooted routing structures plus greedy/load-aware assignment**, while the more elaborate search-heavy methods in **Generation 6**, **Generation 7**, and **Generation 16** all collapse to timeout scores of **-999999999.00**.
- **Within the valid family, better assignment calibration has produced more gain than richer search.** **Generation 12** added Pareto-pruned lambda candidates and multistart local search but scored **5.24**, while **Generation 17** with multi-tree load-aware greedy scoring reached **5.22**, and the current best with bounded multi-tree preprocessing plus slightly stronger queue/energy/utilization calibration improved further to **5.215922**. This continues the prior trend that **server selection objective quality** is at least as important as adding more routing/search complexity.

# META RECOMMENDATIONS

The following are actionable recommendations for the next program generations:

1. **Add regret-aware assignment ordering on top of the current load-aware greedy score.** For each source, evaluate its top two candidate `(server, path)` options under the same marginal score used in assignment, then sort sources by a combination of `work[s]` and the gap between best and second-best score. This directly extends the current best’s strongest component—the calibrated marginal assignment model—and should help reserve scarce low-latency/low-energy server capacity for sources that are hardest to place.

2. **Make candidate pruning server-diverse before applying the global top-12 cap.** Instead of taking the best 12 candidates overall after deduplication, first keep the best 1–2 paths per server (by true `rlat + α*ren` using the task’s actual payload), then truncate globally. This preserves the bounded runtime of the current best while reducing the risk that multiple near-duplicate paths to the same server crowd out useful alternative servers, which is especially relevant because assignment quality has been more important than richer search.

3. **Strengthen the assignment score with an explicit queue externality term based on incremental harm to existing load.** In addition to `queue_delay(pred, mu)`, score candidates with something like `server_load[srv] * (queue_delay(pred, mu) - queue_delay(server_load[srv], mu))` or a small approximation of that effect. This is tightly aligned with the observed success of marginal server-cost modeling and may improve both latency and energy by steering work away from placements that create disproportionate future congestion.

4. **Add a very small targeted non-tree route alternative only for elite source-server pairs.** For each source, take its top 2–3 server candidates from the precomputed trees and generate at most one extra path per server using a fallback Dijkstra that lightly penalizes edges on the primary path, then keep it only if it improves true latency-energy metrics. This follows the prior recommendation of limited route diversity without abandoning the proven server-rooted preprocessing pattern or triggering the timeout behavior seen in heavy multi-profile search methods.

5. **Replace the current one-pass improvement with a restricted server-focused repair pass around hot servers.** After initial assignment, identify the 1–3 most utilized servers or the servers contributing the most queue penalty, and only reconsider tasks assigned there, trying moves to a few precomputed alternative candidates if total marginal score improves. This keeps the current best’s lightweight refinement structure, but concentrates effort where the queue-delay model says the solution is most fragile, which is more promising than broad local search.
