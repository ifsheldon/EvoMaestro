  - route latency `arr_inc * cand["lat"]`

# META RECOMMENDATIONS

The following are actionable recommendations for the next program generations:

1. **Use an exact arrival-weighted server delta in the greedy score, and split “new task” vs “harm to existing tasks.”** Replace the current `new_srv_score - old_srv_score` term with a slightly more explicit decomposition such as: direct queue cost for the new arrival stream plus the incremental queue worsening imposed on already-assigned arrivals, computed from the same `1/(mu-load)` model. This is the closest extension of the best program’s strongest trait—exact load-sensitive assignment—and may tighten the remaining calibration gap in cases where two candidates have similar route cost but different impact on existing server congestion.

2. **Add a tiny dynamic-regret scheduler over a small active frontier instead of a fixed full ordering.** Keep the current multi-start orderings, but for each step or every few steps, recompute best vs second-best candidate scores for only the top `m` unassigned high-impact sources and assign the highest-regret one next. This preserves the current compact-candidate architecture while improving assignment order adaptivity, which is one of the few remaining levers likely to matter in the very tight `5.2159–5.23` band.

3. **Make route compression slightly more quality-aware by preserving one extra “server-saving” alternate for overloaded or near-cap servers.** After per-`(source, server)` Pareto filtering, keep the current best path and tradeoff path, but also allow one additional route only if it reaches a *different server* with materially worse path cost but clearly better projected server economics under current load-sensitive scoring. The current best already wins through aggressive compression; this mutation keeps that compactness while reducing the chance that pruning removes the one route needed to escape a queue hotspot.

4. **Add a bounded hotspot repair phase that targets only the most queue-sensitive servers and evaluates 1- and 2-move repairs exactly.** After the existing greedy plan, rank servers by utilization or `arr/(mu-load)^2`, then only inspect tasks assigned to the top 1–3 hottest servers and test reassignment to compact alternates, including a very small number of pair swaps if single moves stall. This extends the current cheap local search in the most promising direction: concentrated repairs where exact server externalities are largest, without drifting into the brittle broad local-search designs that have underperformed or failed.

5. **Expand the multi-start parameter grid in a structured way around queue sensitivity rather than adding more path-generation complexity.** Keep the same precomputed trees, but test a few extra starts that vary: stronger activation penalties for opening a new server, a steeper post-threshold utilization penalty above `0.75–0.85`, and one or two alternate route-energy weights used only during assignment scoring. The best program already demonstrates that exact end-of-pass rescoring over a small family of constructive regimes is highly effective, so a slightly richer but still disciplined start set is a high-upside mutation.
