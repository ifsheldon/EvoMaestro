# GLOBAL INSIGHTS SCRATCHPAD

The following are global insights about optimization approaches and their effectiveness:

## Successful Algorithmic Patterns
- **The current best result comes from single-tree server-rooted precomputation combined with a stronger marginal assignment model.** The current program, **Precomputed Server-Tree Greedy Routing / current best analyzed code** (**score 5.221813, latency 2.302672, energy 1.963494**), improves slightly over the earlier single-tree variant **Generation 4** (**5.31, 2.33, 1.97**) by keeping the efficient “one Dijkstra tree per server” structure but using a more explicit **marginal latency + marginal energy** assignment score, including projected queue-delay change and server activation cost.
- **Server-rooted preprocessing remains the most consistently successful implementation pattern.** The current best program, **Generation 9**, **Generation 4**, and the earlier top family from the prior insights all avoid per-source/per-server shortest path recomputation. The summaries repeatedly show that this keeps runtime manageable while enabling richer assignment heuristics; the current best preserves this advantage and still reaches the best observed score in this batch at **5.22**.
- **Load-aware greedy assignment with demand-first ordering continues to correlate with the best valid scores.** The current best program sorts sources by `arrival_rate * compute_demand`, tracks projected server load/arrival rate, applies a **95% utilization cap**, and scores each placement using transmission latency, M/M/1-style queue delay, routing energy, dynamic power, and idle-power activation. This same family of ideas appears in **Generation 11** (**5.227055**) and **Generation 13** (**5.23**), confirming that coupling routing and server effects in one greedy decision remains effective.
- **Limited path diversity is useful, but strong assignment scoring can nearly match richer candidate sets.** Previous global insights showed that **multi-tree candidate generation** reached about **5.23** reliably. The current best code uses only **one precomputed tree per server** with weight `latency + 1.5 * energy`, yet slightly edges out the reported **5.23** cluster with **5.221813**, suggesting that improved marginal placement logic can compensate for reduced route diversity when implemented carefully.

## Ineffective Approaches
- **A fixed blended shortest-path weight without a sufficiently strong assignment model underperforms.** **Generation 4** used `base_latency + 0.35 * energy_cost` and a simpler greedy server score, finishing at **5.31, 2.33 latency, 1.97 energy**. Compared with the current best at **5.22**, this supports the evaluator feedback that a fixed path proxy alone does not balance latency and energy well enough.
- **Richer routing logic did not help when implementation correctness failed.** **Generation 10** added top-k candidate restriction and two rounds of local reassignment, but an actual syntax bug (`float("inf"]`) caused validation failure and a **0.0 combined score**. This is the clearest example that heuristic sophistication produced no benefit when path selection could not execute reliably.
- **More elaborate multi-candidate or local-search structures did not automatically beat the current best marginal greedy design.** **Generation 11** (multi-lambda Pareto routing with local search) achieved **5.227055**, and **Generation 13** (three trees plus penalized alternative path and one-pass refinement) achieved **5.23**. Both are valid and reasonably strong, but evaluation feedback says their scalarization and candidate exploration still leave joint latency-energy gains unrealized; neither clearly improves on the simpler current best.
- **Single scalarization remains a recurring limitation across multiple programs.** Even when valid, **Generation 9**, **Generation 11**, and **Generation 13** all received nearly identical feedback: the heuristics are sound but the **fixed weighting / limited candidate exploration / greedy tradeoff model** still leaves room to reduce both latency and energy together.

## Implementation Insights
- **What makes the current best implementation effective is not just precomputation, but the exact form of its marginal objective.** It computes, per assignment,  
  `delta_lat = arr_rate * (path_latency + new_queue_delay) + existing_arrivals * queue_delay_change`  
  and  
  `delta_eng = arr_rate * routing_energy + dyn_power * (load_increase / service_rate) + idle_power_if_activating`.  
  This is a more concrete incremental model than the broader heuristic scoring described for **Generation 4**, and likely explains the improvement from **5.31** to **5.22**.
- **The current best code extracts multiple useful metrics from one Dijkstra pass per server.** For each server tree it stores **combined distance, pure latency, pure energy, and parent pointers**. That lets assignment use latency and energy separately even though the shortest-path tree was built from a blended weight. This is an efficient coding pattern also seen conceptually in earlier strong server-tree methods.
- **Projected load and projected arrival rate are both important state variables in the strongest greedy implementations.** The current best tracks `projected_load` and `projected_arr` separately, allowing it to estimate both utilization impact and queue externality on tasks already assigned to the same server. That is more detailed than a pure load-only heuristic and aligns with its slight edge over **Generation 11** and **Generation 13**.
- **Fallback behavior is implemented conservatively to preserve correctness.** When no feasible server passes the utilization test, the current best falls back to the nearest reachable server in precomputed distance space, otherwise `server_nodes[0]`; it also reconstructs paths directly from stored parents. This kind of defensive implementation helps explain why it passes validation cleanly, unlike **Generation 10**.

## Performance Analysis
- **The current best program is the strongest among the newly listed correct programs, but only by a very small margin.** Its **Graph MOP score 5.221813** slightly beats **Generation 11** at **5.227055**, **Generation 13** at **5.23**, and earlier single-tree **Generation 9** at **5.22 rounded / 2.30 / 1.96**. The differences are tiny, indicating the search is operating on a very tight performance frontier.
- **The biggest measurable gain within the single-tree family came from improving assignment quality, not changing asymptotic structure.** **Generation 4** to the current best reduced score from **5.31 to 5.22**, latency from **2.33 to 2.302672**, and energy from **1.97 to 1.963494**, while keeping the same broad pattern of server-rooted precomputation plus greedy assignment.
- **Multi-candidate path generation no longer shows a decisive advantage over the best single-tree marginal model.** Previous global insights favored the **three-tree** family at around **5.23**, but the current best single-tree implementation slightly outperforms that cluster. The evidence now suggests that the quality of the **server selection objective** can matter at least as much as adding more route candidates.
- **Across all correct programs here, better scores still come from joint improvement, not tradeoff sacrifice.** The top methods all sit near **latency 2.30** and **energy 1.96**, and the current best improves both versus weaker heuristics like **Generation 4**. This matches the evaluator’s repeated note that the main remaining gap is incomplete joint optimization rather than a need to exchange one objective for the other.

# META RECOMMENDATIONS

The following are actionable recommendations for the next program generations:

1. **Keep the one-tree-per-server precomputation, but add a tiny bounded set of alternative server-rooted trees with different routing blends.** For each server, precompute 2–4 trees instead of 1, using weights like `lat + 1.0*eng`, `lat + 2.0*eng`, and `lat + 1.2*eng + small_capacity_penalty`, while still storing pure latency/energy/parents for each tree. This directly extends the strongest pattern—server-rooted preprocessing—while addressing the main remaining weakness repeatedly noted in top programs: limited candidate diversity from a single scalarized route tree.

2. **Upgrade server selection from a single greedy score to a “best-vs-second-best regret” aware assignment order.** Before finalizing assignments, estimate each source’s top two server/path options under the current marginal model and process first the sources with highest `arrival_rate * compute_demand` and largest gap between first and second choice. This builds on the current best’s strong demand-first load-aware greedy logic, but should better preserve scarce high-quality low-latency/low-energy server slots for the tasks that are hardest to place well.

3. **Refine the marginal objective to include a stronger queue externality and a light activation bias for consolidation.** The current best already models `projected_arr[srv] * (q_delay_new - q_delay_old)` well; extend this by adding a small term that estimates the source’s own future waiting sensitivity or slightly penalizes opening a new server unless it gives a clear latency/network-energy gain. This is evidence-based because the best improvements so far came from better incremental assignment modeling, and server activation/queue effects are exactly where the current best gained over earlier single-tree variants.

4. **Add a restricted post-processing reassignment pass focused only on the most impactful sources or servers.** After the initial greedy assignment, revisit only sources with the largest contribution proxy such as `arrival_rate * (path_latency + queue_delay)` or those assigned to the most utilized servers, and test moving them to one of a few alternative precomputed server/tree candidates if total marginal score improves. This keeps the mutation close to the best program’s efficient structure, while borrowing the useful part of local-search ideas from later generations without the overhead and fragility of broad global refinement.

5. **Inject one lightweight non-tree route alternative for only the most promising source-server pairs.** For a small shortlist of candidate servers per source, generate a second path by rerunning a shortest-path search that penalizes edges from the primary tree path, then compare assignments using the same marginal latency/energy model. This is a targeted way to improve path diversity beyond a single shortest-path tree without abandoning the proven O(num_servers) precompute pattern that underlies the current best result.
