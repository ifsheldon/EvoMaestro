# META RECOMMENDATIONS

The following are actionable recommendations for the next program generations:

1. **Replace the current server-load term in `eval_marginal` with an explicit server-state delta, not just a first derivative.** Concretely, compute a queue cost like `Q(load) = load / (mu - load)` or `Q(load) = load * mu / (mu - load)^2` and score `Q(new_load) - Q(current_load)` plus `ALPHA * dyn * (new_load - current_load) / mu`; keep the same `0.98 * mu` feasibility cutoff. This is the most direct extension of the current best program’s strongest feature—load-aware marginal scoring—and targets the likely remaining calibration gap behind the small frontier difference.

2. **Make regret ordering dynamic during assignment instead of freezing it at zero-load initialization.** Recompute regret for a small active pool of unassigned tasks every few assignments, using current `srv_loads` and current best-vs-second-best marginal scores; if full recomputation is too costly, only refresh the top-K most uncertain tasks. This preserves the validated “regret gap” pattern from Generation 21 while aligning priorities with evolving server saturation, which is more promising than switching to size-based or scarcity-heavy ordering.

3. **Keep the 3-tree preprocessing, but store at most one extra alternate candidate per `(source, server)` using explicit Pareto-style filtering.** After reconstructing the three paths, retain the best path plus at most one alternate only if it is path-distinct and offers a materially different latency/energy tradeoff, such as lower latency by a threshold or lower energy by a threshold without being dominated. This follows the evidence that compact candidate diversity helps, while avoiding the unsuccessful pattern of broad path-set expansion seen in later generations.

4. **Add a tightly targeted repair phase focused only on the most stressed servers, using relocate and optional one-step swap moves scored by the same marginal surrogate.** Rank servers by utilization or queue derivative, then revisit only tasks assigned to the top 1–3 hottest servers; try moving each to precomputed alternatives, and optionally test a bounded pairwise swap when both tasks have near-tied second choices. This is more consistent with the best program’s “light refinement” success than broad local search, and it specifically attacks the small residual inefficiencies caused by early assignments under changing loads.

5. **Introduce one adaptive fourth routing mode only when a task or server is clearly payload-sensitive, rather than globally expanding route diversity.** For example, for high-payload tasks or servers attracting many high-payload assignments, run an extra Dijkstra tree with edge weight `lat + w_e * ene + gamma / cap`, where `gamma` is larger than the current `0.1`, and only keep it if it yields a non-dominated path after payload-based recomputation. This builds on the best program’s cheap-precompute / rich-online-evaluation structure and respects the strong evidence that route generation should remain compact and subordinate to assignment quality.
