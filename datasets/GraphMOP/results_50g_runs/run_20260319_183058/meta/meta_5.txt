# GLOBAL INSIGHTS SCRATCHPAD

The following are global insights about optimization approaches and their effectiveness:

## Successful Algorithmic Patterns
- **Server-rooted multi-tree candidate generation is the strongest repeated pattern.** The current best program, **Multi-Tree Greedy Server Routing** (**Gen 1**, score **5.23**, latency **2.30**, energy **1.96**), precomputes **three Dijkstra trees per server** using latency-focused, energy-focused, and balanced edge weights, then deduplicates path candidates. This same structural idea also appears in **Multi-Mode Regret Routing Heuristic** (**Gen 3**, **5.23**, **2.31/1.96**) and **Greedy Server-Rooted Routing Heuristic** (**Gen 8**, **5.23**, **2.31/1.96**), indicating that limited but diverse server-centric path sets consistently outperform single-tree routing.
- **Load-aware greedy assignment materially improved over the initial heuristic.** The move from **Greedy Server Assignment with Weighted Shortest Paths** (**Gen 0**, score **6.05**, **2.57/2.03**) to later methods that explicitly combine **path cost + projected server utilization + queue-delay proxies + compute-energy proxies** yielded a large improvement, with the best score dropping to **5.23** and both latency and energy decreasing.
- **Ordering tasks by heavier demand before assignment is consistently beneficial.** The better-performing programs all process higher-impact tasks first: **Gen 1** assigns heavier tasks first, **Gen 3** uses regret-based selection with demand estimates, and **Gen 8/current best family** ranks by compute-load impact. This aligns with the improved balance in both objectives versus the simpler initial greedy approach.
- **Post-assignment local refinement helps, even when lightweight.** The current best program includes a **one-pass local reassignment refinement**, and **Gen 3** adds **two local-improvement passes**. While this did not beat **5.23**, these variants consistently stayed at the top tier, suggesting that a small reassignment phase helps preserve the gains from the initial load-aware greedy placement.

## Ineffective Approaches
- **Single fixed blended shortest-path trees underperform richer candidate generation.** **Precomputed Server Tree Routing** (**Gen 2**, score **5.29**, **2.33/1.97**) uses only one server-rooted Dijkstra per server with a fixed `latency + 0.4 * energy` weight. It is valid and efficient, but its narrower candidate set trails the multi-tree approaches at **5.23**, supporting the feedback that fixed heuristic weights restrict better latency-energy tradeoffs.
- **A simplistic initial path proxy and weaker balancing produced the worst result.** **Greedy Server Assignment with Weighted Shortest Paths** (**Gen 0**, **6.05**, **2.57/2.03**) uses a single custom edge weight `base_latency + 0.35 * energy_cost` and a heuristic score over hop count/utilization/power. The much worse latency and energy suggest that this path-cost surrogate did not model the true tradeoff well enough.
- **More elaborate assignment logic alone did not outperform the best simple multi-tree greedy variant.** **Multi-Mode Regret Routing Heuristic** (**Gen 3**) introduces regret-based selection, payload-aware scoring, BFS/finality fallbacks, and two refinement passes, yet remains tied at **5.23** rather than improving beyond **Gen 1**. This matches the evaluation note that the surrogate scoring and local search were still not fully Pareto-efficient.
- **Adaptive edge-weight terms did not translate into better outcomes than the best balanced formulation.** **Greedy Server-Rooted Routing Heuristic** (**Gen 8**) adds adaptive scaling of latency, energy, and inverse capacity in server-rooted trees, but still lands at **5.23** with **2.31/1.96**, not beating the simpler three-mode candidate construction from **Gen 1**.

## Implementation Insights
- **What makes the current best program effective is the combination of path diversity with bounded complexity.** It precomputes only **three server-rooted shortest-path trees per server**, reconstructs up to three candidates per source-server pair, and deduplicates them by exact path signature. This keeps runtime manageable while still exposing enough routing diversity to improve the objective versus single-tree methods.
- **The current best program’s scoring is effective because it couples network and server effects in one greedy decision.** Its assignment score blends **path latency/energy**, **queue-delay proxies**, **server power terms**, and a **soft utilization cap**, which is a stronger implementation pattern than Gen 0’s mainly path/hop-driven heuristic and likely explains the large jump from **6.05** to **5.23**.
- **Server-side precomputation is a robust implementation pattern across good solutions.** **Gen 1**, **Gen 2**, **Gen 3**, and **Gen 8** all shift repeated shortest-path work into per-server preprocessing, then reconstruct source-to-server paths via stored parents. Compared with the initial program, this supports richer scoring without excessive recomputation.
- **Current best family implementations use lightweight refinement rather than heavy global optimization.** The analyzed current-best code uses a **one-pass reassignment** with temporary load removal and slight “stickiness” toward the current server. Similar modest refinement in **Gen 1/8** kept top-tier performance, showing that implementation simplicity did not prevent matching the best observed score.

## Performance Analysis
- **The biggest observed gain was from Gen 0 to the multi-tree load-aware family.** Score improved from **6.05** to **5.23**; latency dropped from **2.57** to **2.30**; energy dropped from **2.03** to **1.96**. This is the clearest evidence that combining diversified routing candidates with load-aware assignment substantially improves both objectives simultaneously.
- **The performance frontier is very tight among the best later programs.** **Gen 1**, **Gen 3**, and **Gen 8** all reach **Graph MOP 5.23**, with latency in the **2.30–2.31** range and energy at **1.96**. That clustering suggests these implementations converge on a similar tradeoff quality despite differences in regret logic, adaptive weights, or local search depth.
- **Single-tree precomputation is close but measurably worse.** **Gen 2** at **5.29** trails the current best by **0.06** score, with latency worse by **0.03** and energy worse by **0.01**. This small but consistent gap supports the interpretation that candidate diversity matters more than merely caching shortest-path trees.
- **Across all correct programs, lower score correlates with joint improvement in both latency and energy, not trading one off for the other.** The best programs reduced latency and energy together relative to earlier baselines, matching the evaluator’s repeated feedback that the remaining limitation is not correctness but incomplete joint optimization of the two objectives.

# META RECOMMENDATIONS

The following are actionable recommendations for the next program generations:

1. **Expand the server-rooted candidate set slightly beyond the current three trees, but keep it bounded and deduplicated.** Add 1–2 extra Dijkstra modes per server that specifically target the remaining blind spots of the current best heuristic, such as a stronger capacity-aware balanced weight and a queue-sensitive latency/energy blend (for example, `lat + 0.2*ene + 0.1/cap` and `ene + 0.15*lat + 0.08/cap`). This directly extends the strongest repeated pattern—multi-tree server-rooted candidate generation—while preserving the implementation advantage of small, precomputed candidate pools.

2. **Upgrade candidate diversity by injecting a small number of non-tree alternatives per source-server pair.** After reconstructing the server-tree paths, generate one additional nearby variant for promising server pairs, such as replacing one path segment via a shortest-path search that temporarily penalizes the original edges or computing a second-shortest path under the same mode. Since single fixed trees were slightly worse than richer candidate sets, this is a targeted way to improve path diversity without abandoning the proven server-precomputation structure.

3. **Make assignment scoring marginal-cost based instead of absolute-state based.** In `best_assignment_for_source`, score each option using the *incremental* change caused by placing the task on that server: increase in queue delay, increase in compute energy, and path cost, rather than just the post-assignment totals. This is a natural refinement of the current best program’s coupled network/server greedy score and may better distinguish placements when top-tier methods are already tightly clustered.

4. **Replace the one-pass reassignment with a restricted two-stage local search focused on only the most impactful tasks or overloaded servers.** Keep the current lightweight refinement, but add a second pass that revisits either the top-k highest-demand tasks or tasks assigned to the most utilized servers, allowing reassignment only if both latency and energy proxies improve or if total score improves by a clear margin. This builds on the evidence that lightweight local refinement helps, while avoiding the complexity of heavy global optimization that has not outperformed the best greedy multi-tree variant.

5. **Introduce a stronger task ordering policy that mixes demand, payload, and assignment difficulty.** Instead of sorting only by `arrival_rate * compute_demand` and payload, compute a priority such as high demand first, then break ties by “regret” between the best and second-best server scores or by fewest reachable distinct candidates. The global results suggest heavy-first ordering is valuable, and adding a difficulty-aware tie-breaker is a low-risk way to better reserve scarce high-quality server/path options for the tasks that need them most.
