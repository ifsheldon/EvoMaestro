# GLOBAL INSIGHTS SCRATCHPAD

The following are global insights about optimization approaches and their effectiveness:

## Successful Algorithmic Patterns
- **The current best remains Generation 21 / `regret_activation_routing`, with the strongest fully specified result at `5.215922` (`latency 2.304111`, `energy 1.959833`).** Its advantage is still best explained by the exact combination visible in code:  
  - **3 bounded server-rooted Dijkstra modes** using latency-focused, energy-focused, and balanced weights, each with a small capacity term `0.1 / cap`,  
  - **payload-aware path metric recomputation** after parent-tree reconstruction via `get_path_metrics`,  
  - **regret-ordered assignment** using the gap between best and second-best candidate scores,  
  - **marginal server-load scoring** with queue derivative and dynamic server energy.  
  This package still edges out nearby valid competitors such as Generation 22 (`5.22`), Generation 30 (`5.22`), Generation 28 (`5.227055`), and Generation 32 (`5.23`).

- **State-aware assignment quality continues to matter more than adding more route diversity.** Generation 22 / `regret_marginal_refiner` scored `5.22` with **3 trees + regret order + marginal server-load model**, while Generation 28 / `capacity_regret_router` used **4 trees, pruning, and 3-pass local search** but landed slightly worse at `5.227055`. This reinforces the earlier global pattern: **a better-calibrated marginal assignment objective beats simply expanding candidate-path machinery**.

- **Compact multi-tree preprocessing remains the dominant successful routing pattern.** Across strong valid programs, the competitive cluster all uses a **small fixed set of server-rooted shortest-path trees**:
  - Generation 21: **3 weighted modes in code**, best at `5.215922`
  - Generation 22: **3 modes**, `5.22`
  - Generation 18: **6 heuristic trees**, `5.24`
  - Generation 28: **4 modes**, `5.227055`
  - Generation 32: **multi-alpha trees**, `5.23`  
  The evidence remains that **bounded route diversity helps**, but only when paired with strong downstream scoring.

- **Regret-aware or feasibility-aware ordering consistently outperforms simpler descending-demand greedy placement.** Generation 22’s regret-guided assignment reached `5.22`, and the current best Generation 21 improves slightly further with a more explicit marginal-load regret computation. By contrast, Generation 30 / `marginal_cost_balanced_routing`, which is mainly **descending arrival-rate×compute-demand greedy**, tied at `5.22` but did not surpass the best. The difference is small, but consistent with prior evidence that **regret is beneficial when based on current marginal load, not just static task size**.

## Ineffective Approaches
- **Adding more path-generation modes without stronger assignment calibration did not improve the frontier.** Generation 18 / `marginal_objective_routing` used **6 Dijkstra trees per server** plus two local-improvement passes, yet scored only `5.24` (`2.30 / 1.97`). Generation 28 also increased route complexity with **4 trees and 3-pass reinsert search**, but still scored `5.227055`. This matches prior findings from Generation 24: **more candidate routes alone do not beat the current best if placement scoring is weaker**.

- **Single blended routing weights plateau slightly behind the top methods.** Generation 30 / `marginal_cost_balanced_routing` used one server-rooted Dijkstra weight of `latency + 1.25 * energy`, achieving `5.22` (`2.30 / 1.96`) but not improving on the best. This is consistent with the earlier underperformance of fixed-weight Generation 5 (`5.30`): **fixed or weakly adaptive path weighting limits joint latency-energy improvement**.

- **Local search by itself has not produced gains when the underlying surrogate is less sharp.** Generation 32 / `capacity_regret_routing` added relocation, limited swaps, and repair, but scored `5.23` (`2.31 / 1.96`). Generation 18 also used two improvement passes and remained at `5.24`. Relative to Generation 21, this suggests that **small search neighborhoods help only when the assignment objective already captures activation/load tradeoffs accurately**.

- **Weaker routing/cost blending shows up directly in evaluator feedback as simultaneous latency-energy stagnation.** For Generations 18, 22, 28, 30, and 32, the evaluator repeatedly notes that the solution is valid and balanced, but still leaves room to **lower both latency and energy together**. That recurring feedback indicates a common limitation: **proxy cost formulations that are reasonable but not quite calibrated enough to move both objectives at once**.

## Implementation Insights
- **What makes the current best program effective is the very specific cheap-precompute / richer-online-score split.** In code, Generation 21:
  - builds one undirected adjacency list and `edge_map`,
  - runs only **3 server-rooted Dijkstra passes per server**,
  - reconstructs candidate paths from parent arrays,
  - then recomputes actual payload-sensitive route metrics with `get_path_metrics`.  
  This preserves runtime safety while avoiding the weakness of scoring candidates only by tree distance.

- **The best program’s assignment surrogate is still its clearest implementation strength.** `eval_marginal` combines:
  - transmission cost `arr * (p_lat + ALPHA * p_ene)`,
  - server load increase `arr * comp`,
  - **queue sensitivity via derivative-like `mu / (mu - load)^2`**,
  - **dynamic server energy via `dyn / mu`**,  
  plus a hard rejection near `0.98 * mu`. This remains more informative than lighter heuristics in Generation 30 and appears to explain why the best code slightly beats other near-ties in the `5.22–5.23` band.

- **The current best uses regret in a more operational way than several neighboring variants.** It computes an initial per-source regret from the gap between best and second-best candidate scores, then assigns in descending regret order under evolving `srv_loads`. This is a stronger form of the pattern also present in Generation 22 and Generation 28, and it appears to outperform approaches that sort mainly by task size or use less state-sensitive ordering.

- **Candidate-path handling is intentionally compact and deduplicated, which aligns with both correctness and score stability.** The current best stores only unique reconstructed paths per `(source, server)` from a tiny set of trees, then performs one refinement pass with incremental load updates. This is a simpler but more disciplined version of the broader multi-tree strategy used by Generations 18, 22, 28, and 32, and the results suggest that **small candidate sets plus clean marginal evaluation are enough to stay at the top of the valid cluster**.

# META RECOMMENDATIONS

The following are actionable recommendations for the next program generations:

1. **Keep the current 3-tree preprocessing, but store up to 2 deduplicated candidates per `(source, server)` with explicit tradeoff filtering.** Retain the best payload-recomputed path plus at most one alternate only if it is meaningfully different in hop sequence and offers a different latency/energy balance, rather than just a tiny weighted-distance variation. This is a low-risk extension of the winning compact candidate-set pattern and is more promising than adding many more route modes, which recent generations showed does not help by itself.

2. **Strengthen `eval_marginal` with a small congestion-externality term that reflects harm to existing jobs, not just the new task’s own queue penalty.** A concrete mutation is to score server impact as the change in a server-state cost, e.g. `F(load)=load/(mu-load)` or a second-order approximation, and add `F(new_load)-F(old_load)` instead of only `load_increase * mu/(mu-load)^2`. This directly builds on the current best’s strongest feature—state-aware marginal load scoring—and targets the observed frontier limitation that cost proxies are still slightly under-calibrated.

3. **Make regret ordering dynamic and scarcity-aware rather than using a one-time initial regret computed at zero load.** Recompute regret for a small frontier of unassigned tasks during assignment, or augment each source’s priority by the number of currently feasible low-cost servers/candidates under present `srv_loads`. This preserves the proven advantage of regret-based ordering while making it better aligned with evolving server saturation, which matches the evidence that operational regret beats static size-based greedy rules.

4. **Add a hotspot-focused repair phase that only revisits tasks on the 1–3 most stressed servers, using relocate and one-step swap checks.** Rank servers by current queue derivative, utilization ratio, or total marginal server-state contribution, then test moving their heaviest-regret or highest-load tasks to precomputed alternatives; optionally allow a bounded swap if both tasks improve combined marginal score. This is a better fit than broad local search because recent results suggest repair helps only when it is tightly targeted by the same strong surrogate that made the current best successful.

5. **Introduce one adaptive extra routing mode per server tied to payload/capacity sensitivity, not a blanket increase in route diversity.** For example, add a fourth Dijkstra pass with a stronger `payload-like` capacity penalty such as `lat + w_e*ene + gamma/cap` for sources with high payload or for servers serving many high-payload tasks, while keeping the rest of the pipeline unchanged. This follows the evidence that compact multi-tree routing remains strong, but that any route expansion should be narrowly targeted and subordinate to the assignment model rather than replacing it.
